## 1. Research & Context
- **Official Documentation**: Codex CLI documentation, internal SQLite schema (`thread_history_1.sqlite`), and empirical rollout research from `T2.1-codex-research.md`.
- **Agent / Tooling Versions**: Codex CLI `0.166.0` (with backward compatibility across legacy `0.14.0`, `0.18.0`, `0.166.0` rollouts and compressed `.jsonl.zst`), Rust 1.86 / 1.99 nightlies, SQLite 3.x.
- **Established Facts**:
  - `~/.codex/thread_history_1.sqlite` indexes turns and items:
    - `thread_turns`: `(thread_id, turn_id, rollout_ordinal, status, started_at, completed_at)`
    - `thread_items`: `(thread_id, turn_id, item_id, rollout_ordinal, item_type, item_json)`
    - Item types present in SQLite: `userMessage`, `agentMessage`, `reasoning`, `commandExecution`, `fileChange`, `mcpToolCall`, `dynamicToolCall`, `collabAgentToolCall`, `functionCallOutput`.
  - Rollout files (`~/.codex/sessions/**/rollout-*.jsonl` and `.jsonl.zst`) record historical streaming events.
  - Streaming incremental scanning via `BufReader` and `zstd::Decoder` maintains bounded memory overhead: headers are collected in pass 1, and detailed JSON item payloads are parsed strictly for turns within the requested pagination slice.
  - Turn and item deduplication: `response_item` and subsequent `event_msg(item_completed)` share item IDs (`call_id` / `id`), ensuring identical items are updated in place rather than duplicated.

## 2. Design & Acceptance Criteria
- **Scope & Changes**:
  - Implement dual-engine history reader in `crates/session-core/src/codex/history.rs`:
    1. Primary SQLite Reader: Direct SQL `LIMIT`/`OFFSET` queries on `thread_turns` and `thread_items` sorted by `rollout_ordinal`. Zero full-file memory allocations.
    2. Streaming Rollout Parser Fallback: Incremental line-by-line reading with on-the-fly decompression for `.jsonl` and `.jsonl.zst`.
  - Normalization: Map all Codex item types into `shardrail_protocol::NormalizedItem` (`UserMessage`, `AgentMessage`, `Reasoning`, `CommandExecution`, `FileChange`, `ToolCall`, `Notice`).
  - Pagination: Cursor-based pagination (`ord:<ordinal>`) supporting forward and backward paging, `has_more`, and total turn counts.
  - Integrity & Performance: Preserve ordering, deduplicate item completions, handle exotic Unicode/escapes, and maintain deterministic SHA-256 hash across repeated queries.
- **Acceptance Criteria**:
  - [x] Paged reading of all messages/events, including tool calls, diffs, command outputs, with no loss and no duplicates.
  - [x] Large sessions are not loaded whole into memory (streaming and SQL pagination).
  - [x] Comparison with source (counts, checksums) on sessions of thousands of records.
  - [x] Unusual Unicode, Cyrillic, emoji, and control character preservation verified.
  - [x] Deterministic ordering and checksum fidelity across multiple reads.
