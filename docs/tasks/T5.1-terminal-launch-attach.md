## 1. Research & Context

### 1.1 Technical Background & Operating System Boundaries
Terminal-based agent control in Shardrail requires a robust mechanism for launching, observing, and interacting with interactive CLI agents (specifically Codex CLI and Claude Code) across macOS (Darwin) and Linux host machines.

The research investigates three distinct operational models:
1. **Option (a) Daemon-Managed PTY**: The Shardrail daemon (`shardraild`) allocates an open pseudoterminal master/slave pair (`posix_openpt` / `openpty`), forks the agent process under the slave PTY, maintains process ownership across network disconnects, and streams terminal I/O over UNIX domain sockets / WebSockets to connected browser instances.
2. **Option (b) CLI Wrapper (`shardrail run <agent>`)**: The user starts the agent inside their interactive shell through a wrapper CLI. The wrapper allocates a local PTY, mirrors raw I/O to the local user terminal, and binds an auxiliary local UNIX domain socket allowing the daemon / web clients to attach concurrently as observers or interactive peers.
3. **Option (c) Arbitrary Terminal Process Hijacking**: The user starts the agent manually in an unmanaged terminal emulator (Terminal.app, iTerm2, Alacritty, GNOME Terminal) or multiplexer (`tmux`). Shardrail attempts to dynamically take over process file descriptors or inject keystrokes into the existing tty using system debugging APIs or tty ioctls.

### 1.2 Operating System & Security Mechanisms Evaluated

| Mechanism / Capability | macOS Darwin (Sonoma 14.x / Sequoia 15.x / Darwin 27.x) | Modern Linux (Kernel 6.x+, Ubuntu 24.04, Debian 12) |
|---|---|---|
| **PTY Allocation (`openpty`)** | Fully supported in standard POSIX (`util.h`). No elevated privileges required for child processes owned by current user. | Fully supported in standard POSIX (`pty.h`). Master/slave nodes in `/dev/pts/`. Unprivileged user execution. |
| **`TIOCSTI` Keystroke Injection** | Blocked or heavily restricted unless running as root with disabled sandbox protections; completely blocked under macOS hardened runtime. | **Disabled by default** in modern Linux kernels via `dev.tty.legacy_tiocsti=0` (sysctl introduced in Linux 6.2+). Enabling requires host-level root configuration. |
| **Process Hijacking (`reptyr` / `ptrace`)** | **Permanently blocked** by System Integrity Protection (SIP) and hardened Mach task ports (`task_for_pid`). Unsigned processes cannot attach ptrace to running binaries even under `sudo`. | Blocked by default via Yama LSM (`/proc/sys/kernel/yama/ptrace_scope > 0`). Attaching requires `PTRACE_MODE_ATTACH_REALCREDS` or root capabilities. |
| **Terminal Multiplexer (`tmux`)** | Fully viable if `tmux` is installed. Allows headless sessions (`tmux new-session -d`) and shared socket attachment (`tmux -S <socket> attach`). Not installed by default. | Fully viable if installed. Identical behavior to macOS via named UNIX domain sockets. Not installed on minimal container images. |
| **Window Resize (`TIOCSWINSZ`)** | Supported on master PTY fd via `ioctl(master_fd, TIOCSWINSZ, &ws)`. Child receives `SIGWINCH`. | Supported on master PTY fd via `ioctl(master_fd, TIOCSWINSZ, &ws)`. Child receives `SIGWINCH`. |

## 2. Design & Acceptance Criteria

### 2.1 Evaluated Architectural Options

#### Option (a): Daemon-Managed PTY (`shardraild` as Process Supervisor)
- **Architecture**:
  - The daemon spawns the target agent binary using an allocated PTY master/slave pair.
  - The daemon retains the master fd in its async event loop (`tokio` in Rust / `selectors` in Python).
  - Terminal output is held in a bounded in-memory circular scrollback ring buffer (e.g. 64 KB – 512 KB).
  - Multiple remote web clients connect over authenticated WebSocket channels.
  - Terminal resizing is negotiated: remote browser sends `MSG_RESIZE(rows, cols)` which updates the master PTY geometry via `TIOCSWINSZ`.
- **Local User Terminal Visibility**:
  - The process has no attached native host terminal window unless the user opens one and runs `shardrail attach <session_id>`.
  - Full decoupling from local terminal lifecycles: closing the browser, terminal window, or SSH session leaves the agent execution alive.
- **Screen Sync & Input**:
  - Clean byte-level multiplexing. Remote input bytes are written directly to the PTY master fd.
  - On client connect, the circular buffer replays the most recent terminal escape sequences, allowing xterm.js to render the current screen state cleanly.
- **Failure Modes & Breakages**:
  - None at OS level. Process isolation is clean.
  - Dual resizing: if two browser tabs with different viewport dimensions connect simultaneously, the active PTY size matches the last received resize event.
- **Security Assessment**:
  - **Highest security profile**. Daemon runs strictly with user permissions; no elevated capabilities, no ptrace, no kernel sysctl alterations needed.

#### Option (b): CLI Wrapper (`shardrail run <agent>`)
- **Architecture**:
  - User runs e.g. `shardrail run codex` or `shardrail run claude` in their terminal emulator of choice.
  - The wrapper binary allocates an inner PTY, sets the outer terminal to raw mode (`termios`), and bridges raw bytes bidirectionally between inner PTY and outer stdin/stdout.
  - Simultaneously, the wrapper exposes a local UNIX domain socket (e.g. `/tmp/shardrail-<session>.sock`) managed by the wrapper process.
- **Local User Terminal Visibility**:
  - Fully visible in the user's native terminal (iTerm2, Terminal.app, tmux).
  - The user types directly in their local terminal while the remote web browser watches and interacts.
- **Screen Sync & Input**:
  - Dual interactive control: both local user keystrokes and remote WebSocket keystrokes write to the inner master PTY fd.
  - Output broadcasts concurrently to local stdout and connected remote sockets.
- **Failure Modes & Breakages**:
  - If the user closes their native terminal emulator (window closed / laptop lid closed / SSH disconnect), SIGHUP terminates the wrapper process, killing the agent unless wrapped in nohup/disown or managed by a daemon helper.
  - Raw mode terminal state cleanup: if the wrapper crashes abruptly, the host terminal remains in raw mode until `reset` or `stty sane` is run.
- **Security Assessment**:
  - Clean unprivileged execution. UNIX domain socket permissions must be restricted to `0600` (user-only).

#### Option (c): Dynamic Hijacking of Unmanaged Existing Process
- **Architecture**:
  - The user launches `codex` or `claude` in an arbitrary terminal tab.
  - Shardrail attempts to inject into the process using `reptyr` (via `ptrace(2)`) or inject keystrokes via `ioctl(TIOCSTI)`.
- **macOS Darwin Empirical Reality**:
  - **Hard Blocker**: macOS System Integrity Protection (SIP) and Apple Silicon security architecture strictly prohibit `task_for_pid` cross-process memory manipulation without entitlements and SIP disabling. `reptyr` does not work on modern macOS.
  - `ioctl(TIOCSTI)` on Darwin requires root or is denied across process boundaries.
- **Linux Empirical Reality**:
  - Linux Kernel 6.2+ introduced `dev.tty.legacy_tiocsti=0` by default (e.g. Ubuntu 24.04, Debian 12, Fedora 39+), rejecting all `ioctl(fd, TIOCSTI, ...)` calls with `EPERM`.
  - `reptyr` requires `kernel.yama.ptrace_scope = 0` and frequently corrupts terminal line disciplines of complex ncurses/React Ink TUI engines (such as Claude Code's Ink interface and Codex's rich terminal renderers).
- **Security Assessment**:
  - **Extremely hazardous & brittle**. Requires compromising host kernel security postures (disabling SIP or relaxing Yama ptrace).
- **Definitive Conclusion**:
  - **Option (c) direct hijacking is completely rejected** as an engineering path.

### 2.2 Compatibility with the "Session is a File" Model (Stages 2–4)
A central architectural pillar of Shardrail is the "session is a file" model established in Stages 2–4:
- Codex persists sessions in `~/.codex/sessions/rollups/<session_id>.jsonl`.
- Claude Code persists sessions in `~/.claude/projects/<project>/<session_id>.jsonl`.

Can read-from-files plus managed launch for writing be enough?
- **Yes, absolutely**:
  1. **Passive Read/Inspection**: For observing agent turns, reading full conversation histories, and watching streaming text in the Shardrail web UI, file-tailing and journal replication (Stages 2–4) remain the primary, non-invasive, zero-overhead mechanism.
  2. **Interactive Terminal View**: The terminal PTY is required only when the user explicitly requests full interactive terminal fidelity (interactive TUI menus, raw control character interaction, vi-mode navigation, or approval prompts rendered exclusively in terminal UI).
  3. **Bidirectional Continuity**: Both Codex and Claude Code CLI support native resumption from session files:
     - `codex resume <session_id>`
     - `claude resume <session_id>`
  This guarantees that a session can transition between passive file tracking and an active managed PTY without data loss.

### 2.3 Stop and Resume Under Shardrail for Unmanaged Sessions
When a user begins an agent session manually in an arbitrary terminal (unmanaged by Shardrail) and later wants to bring it under Shardrail control:

#### What is Lost vs. What is Kept
1. **Kept (100% Context Integrity)**:
   - Full conversational transcript, system prompt, tool invocations, files read/modified, and project configuration. All of this is safely flushed to the session JSONL file on disk by the agent CLI at every message boundary.
2. **Lost (Transient Running Turn State)**:
   - If the agent is actively executing a shell command or streaming an LLM response at the exact second of termination, that in-flight turn is interrupted.
   - The unmanaged process's ephemeral memory and raw terminal scrollback history not yet committed to the session file.

#### Safe & Explicit UI Workflow
To handle unmanaged processes gracefully without risking corrupt state:
1. **Detection**: Shardrail monitors running processes (`pgrep -f "codex|claude"`) and matches active working directories and session file locks.
2. **Indication**: The web UI flags the session as `Active (External Terminal — Read Only)`.
3. **User Action**: The UI provides a clear action button: `Take Over in Shardrail`.
4. **Safety Confirmation Modal**:
   ```text
   ┌─────────────────────────────────────────────────────────────┐
   │ Take Over Agent Session                                     │
   │                                                             │
   │ An active Codex session was detected in an external        │
   │ terminal.                                                   │
   │                                                             │
   │ • Saved Context: 14 completed turns preserved               │
   │ • Running Turn: Will be cleanly interrupted                 │
   │                                                             │
   │ Shardrail will signal the external process to stop and      │
   │ resume the session inside a managed Shardrail PTY.          │
   │                                                             │
   │ [ Cancel ]                       [ Stop & Resume Here ]     │
   └─────────────────────────────────────────────────────────────┘
   ```
5. **Execution**:
   - Send `SIGINT` to allow graceful turn termination; if unresponsive after 3s, send `SIGTERM`.
   - Wait for lock file release in `~/.codex/` or `~/.claude/`.
   - Invoke `shardraild` to launch `codex resume <session_id>` (or `claude resume <session_id>`) inside a Managed PTY (Option a).
   - Seamlessly transition the web UI from read-only journal stream to interactive xterm.js terminal.

## 3. Implementation Summary & Prototypes

Functional working prototypes were implemented and verified in `Shardrail_Web/prototypes/t5.1-terminal-attach/`:

1. `common.py`:
   - POSIX PTY allocation helper (`fork_pty_child`) configuring slave terminal session, controlling tty (`TIOCSCTTY`), and standard descriptor redirection.
   - PTY window size adjustment (`set_pty_size`) via `TIOCSWINSZ`.
   - Length-prefixed binary framing protocol:
     - `MSG_DATA = 1` (terminal stdout/stderr stream)
     - `MSG_INPUT = 2` (terminal stdin stream from web client)
     - `MSG_RESIZE = 3` (terminal window dimensions: `rows`, `cols` as uint16)
   - Resilient frame parser (`read_available_frames`) and timed frame collector (`recv_frames_timed`).
   - Clean lifecycle stepper loop (`run_stepper_loop`) and graceful teardown (`teardown_stepper`).

2. `daemon_pty_server.py` & `client_attach.py` (Option a Prototype):
   - Implements a daemon PTY supervisor managing a child shell process.
   - Multi-client broadcast with scrollback ring buffer replay upon attachment.
   - Tested under `run_prototype_a.py`: verifies initial attach, input echo, window resizing (`40x100`), disconnect, re-attach, and scrollback replay integrity.

3. `cli_wrapper.py` & `run_prototype_b.py` (Option b Prototype):
   - Implements a CLI wrapper wrapping an interactive child process in a PTY while providing a dual-attach UNIX domain socket.
   - Tested under `run_prototype_b.py`: verifies child process execution, local terminal passthrough, remote socket connection, remote input injection, and echo reception.

## 5. Architectural Comparison Matrix

| Evaluation Dimension | Option (a): Daemon-Managed PTY | Option (b): CLI Wrapper (`shardrail run`) | Option (c): Dynamic Hijacking |
|---|---|---|---|
| **macOS Darwin Compatibility** | **100% Native POSIX** (no special privileges) | **100% Native POSIX** (no special privileges) | **0% Incompatible** (Blocked by SIP / hardened runtime) |
| **Modern Linux Compatibility** | **100% Native POSIX** | **100% Native POSIX** | **0% Incompatible** (Blocked by `legacy_tiocsti=0` & Yama) |
| **Terminal Disconnect Resilience** | **Complete resilience**: Agent runs independent of user terminal / browser tab | **Vulnerable**: Closing user terminal sends SIGHUP to wrapper | **Vulnerable**: Hijacked master fd terminates if original window closes |
| **Multi-Client Attach / Web UI** | Clean multiplexing via daemon WebSocket | Clean multiplexing via wrapper socket | Extremely fragile / erratic screen state |
| **Screen State Replay on Reconnect** | Circular ring buffer or virtual terminal emulator (headless xterm) | Circular ring buffer | Cannot inspect historical tty buffers |
| **Maintenance Burden** | Moderate (Standard daemon subsystem in `shardraild`) | Low-to-Moderate (Small CLI wrapper binary) | Prohibitive (OS-specific reverse engineering) |

## 6. Recommendations & Decisions Required from Owner

### 6.1 Architectural Recommendation
1. **Primary Foundation: Option (a) Daemon-Managed PTY**:
   - `shardraild` should implement the native PTY management layer for all agent sessions launched from or controlled by the Shardrail web UI.
   - Provides unshakeable process isolation, persistent execution across network drops, and native multi-browser streaming.
2. **Developer Ergonomics: Option (b) `shardrail run <agent>` as Secondary Adapter**:
   - For users who prefer launching commands directly inside their physical terminal shell, provide the lightweight `shardrail run` wrapper.
   - The wrapper registers the session with `shardraild` and proxies I/O to the daemon's WebSocket relay.
3. **External Terminal Policy**:
   - Adopt the "Stop and Resume under Shardrail" workflow described in Section 2.3 for any agent started without `shardrail run`.

### 6.2 Explicit Owner Decision Points
Before proceeding with T5.3 implementation, the owner must confirm:
- **Decision 1**: Approve **Option (a)** as the primary backend architecture for T5.3 terminal execution.
- **Decision 2**: Approve building **Option (b)** (`shardrail run`) as an optional companion CLI launcher for interactive developer terminal workflows.
- **Decision 3**: Confirm the explicit UI "Stop and Resume under Shardrail" policy for external unmanaged sessions (discarding Option c hijacking permanently).
