### 1.2 Storage Location, Hierarchy & Format

#### Filesystem Layout
Codex stores all session data in `~/.codex/` (`$CODEX_HOME`):

```text
~/.codex/
├── session_index.jsonl               # Quick thread index (id, thread_name, updated_at)
├── state_5.sqlite                    # Master thread metadata database (SQLx)
├── thread_history_1.sqlite           # Projection database indexing turns/items by byte offsets
├── queue_1.sqlite                    # Task execution queue
├── goals_1.sqlite                    # Goal tracking
├── thread-writer-locks/              # POSIX advisory locks for active threads
│   ├── .coordination.lock            # Global writer coordination lock
│   └── <thread_id>.lock              # Per-thread advisory flock file
├── ipc/
│   └── ipc.sock                      # Local IPC domain socket for GUI/CLI
├── app-server-control/
│   └── app-server-control.sock       # Headless app-server daemon socket
├── archived_sessions/                # Archived session rollouts
└── sessions/
    └── YYYY/
        └── MM/
            └── DD/
                ├── rollout-YYYY-MM-DDTHH-MM-SS-<UUID>.jsonl      # Source-of-truth session log
                ├── rollout-YYYY-MM-DDTHH-MM-SS-<UUID>.jsonl.zst  # Compressed session log (Zstandard)
                └── rollout-..._<SUB_UUID>.jsonl                 # Sub-agent session log
```

#### Empirical Storage Metrics (Tested on Live Machine)
- **Total session files**: 3,930 sessions
  - Active plaintext JSONL: 330 files
  - Compressed Zstandard: 3,600 files (`.jsonl.zst`)
- **Total storage consumed**: 2,707.89 MB (~2.7 GB)
  - Average file size: 705.57 KB
  - Maximum file size: 126.15 MB
- **Compression**: Codex runs a background compression loop (`codex_rollout::compression`) that compresses older rollouts using Zstandard (`zstd`). Compressed files decompress cleanly with standard `zstd -d -c`.

#### Record Format & Schema
Each rollout file is an append-only JSON Lines (`.jsonl`) stream. Every line contains:
```json
{
  "timestamp": "2026-10-31T20:20:00.000Z",
  "ordinal": 0,
  "type": "<record_type>",
  "payload": { ... },
  "metadata": { ... }
}
```

#### Discovered Record Types
Empirical inspection of active and archived rollouts revealed 8 primary record types:

1. `session_meta`: Initial session header and configuration:
   - Fields: `id`, `timestamp`, `cwd`, `cli_version`, `source` (`cli`, `vscode`, `exec`, `appServer`, etc.), `model_provider`, `model`, `sandbox_policy`.
2. `turn_context`: Context provided at the start of a turn:
   - Fields: `turn_id`, `turn_kind`, `started_at_ms`, `user_input`, `inherited_context`.
3. `response_item`: Content emitted during turns. Payloads have their own `type` discriminator:
   - `message`: User, assistant, or developer role messages with formatted text content.
   - `reasoning`: Chain-of-thought tokens. Contains `summary: []`, `content: null`, and an encrypted API blob `encrypted_content` (length ~2,680 bytes).
   - `function_call`: Tool invocation requests (`name`, `arguments`, `call_id`).
   - `function_call_output`: Tool results (`output`, `call_id`).
   - `custom_tool_call` & `custom_tool_call_output`: Extended tool and MCP invocations.
   - `agent_message`: Inter-agent progress announcements.
4. `world_state`: Snapshot of the active workspace environment:
   - Fields: `git_sha`, `git_branch`, `git_origin_url`, workspace root paths.
5. `token_usage_record`: Token counts per turn:
   - Fields: `turn_token_usage` (`prompt_tokens`, `completion_tokens`, `cached_tokens`), `thread_token_usage`.
6. `compacted`: Compaction event indicating conversation history summarization:
   - Fields: `compacted_turn_ids`, `summary`, `retained_items`.
7. `event_msg`: Runtime diagnostic and status events:
   - Fields: `level`, `message`, `module`.
8. `inter_agent_communication_metadata`: Metadata for subagents spawned via `spawn_agent` and `send_message`.

#### Format Stability Across Versions
- `state_5.sqlite` on the test host contains sessions generated across **55 distinct CLI versions**, spanning from `0.122.0-alpha.13` through `0.166.0`.
- All session rollouts remain compatible and indexable.
- Running `codex migrate-rollouts --json` verified all 3,930 sessions report `status: "already_paginated"`.
- Migrations are tracked internally via SQLx (`_sqlx_migrations` table) and projection offsets in `thread_history_1.sqlite`.

### 1.3 `codex app-server` Protocol & Capabilities

#### Transport Endpoints
`codex app-server` supports three communication modes via `--listen`:
1. `stdio://` (default): Bidirectional JSON-RPC 2.0 over standard input/output. Ideal for local daemon integration.
2. `unix://<PATH>`: Unix domain socket (e.g. `~/.codex/app-server-control/app-server-control.sock`).
3. `ws://<IP>:<PORT>`: WebSocket server with authentication (`capability-token` or `signed-bearer-token`).

#### RPC API Methods (Client -> Server)
- **Thread Operations**:
  - `thread/list`: Lists threads with pagination (`cursor`, `limit`), sorting, and filters (`sourceKinds`, `archived`, `cwd`, `modelProviders`, `useStateDbOnly`).
  - `thread/read`: Reads thread metadata. Includes option `includeTurns: false` for fast metadata-only reading.
  - `thread/resume`: Resumes a thread by `threadId`, `path`, or in-memory `history`. If `threadId` matches an already running thread, `app-server` rejoins the existing thread transparently.
  - `thread/start`: Initializes a brand new conversation thread.
  - `thread/fork`: Forks a thread from a specific turn.
  - `thread/archive`, `thread/unarchive`, `thread/delete`: Lifecycle management.
  - `thread/turns/list`, `thread/items/list`: Paginated historical reading without loading full files into memory.
- **Turn Execution & Mutations**:
  - `turn/start`: Initiates a new prompt turn on a thread with structured input (`text`, `images`, `local_images`).
  - `turn/steer`: Injects steering instructions into an in-flight active turn (`expectedTurnId`).
  - `turn/interrupt`: Aborts the active turn cleanly without corrupting the session.
- **Configuration**:
  - `config/read`, `config/update`, `config/value/write`: Live runtime settings adjustment.

#### Streaming Notifications (Server -> Client)
- `thread/updated`, `thread/started`, `thread/closed`
- `thread/turn/started`, `thread/turn/completed`
- `thread/item/created`, `thread/item/updated`, `thread/item/completed`
- `turn/progress`: Live execution indicators
- `command/exec/output`, `process/stdout`, `process/stderr`: Real-time streaming command outputs

#### Approvals Architecture (Server -> Client Requests)
When configured with approval requirements, `app-server` pauses execution and sends an RPC request to the client:
- `item/commandExecution/requestApproval`: Approval for executing shell commands.
- `item/fileChange/requestApproval`: Approval for modifying or patching files.
- `item/permissions/requestApproval`: Sandbox permission escalations.
- `item/tool/requestUserInput`: Interactive questions asked to the user.
The client responds with `{ decision: "accept" | "reject" | ... }`.

#### Comparison: Files vs `app-server`
| Aspect | Direct File Access (`rollout-*.jsonl`) | `codex app-server` |
|---|---|---|
| **Primary Role** | Historical audit trail, cold hydration | Live interactive control plane |
| **Process Needed** | None (direct filesystem read) | Child process or daemon socket |
| **Approvals** | None (passive reader) | Fully supported interactive RPC |
| **Streaming** | Requires filesystem tailing / inotify | Native real-time push notifications |
| **Writing / Resuming**| Dangerous (bypasses locks/SQLite) | Canonical, safe, concurrency-checked |
| **Compression** | Must handle `.zst` decompression | Transparent hydration |

### 1.4 Multi-Process Sharing & Storage Boundaries

#### Shared Storage
- Both the Codex CLI (`codex`) and GUI (`ChatGPT.app` / `CodexCLI.app`) share the exact same `~/.codex/` storage path.
- The GUI process connects to an embedded `codex app-server` spawned with socket pairs on stdio.
- `thread/list` executed on a standalone `app-server` returned threads created from `vscode`, `cli`, and `exec`.

#### Reading Active Sessions
- **Empirical Test**: We read all 757 lines from an active session rollout file (`01a1939d-22a3-7471-8d9b-d7511a9129a6.jsonl`) while its lock was held exclusively by running process PID 11958.
- **Result**: Read completed with zero errors or delays. Unix file read operations do not block on POSIX advisory locks. Third-party readers (like Shardrail) can safely inspect and tail active sessions without interfering with the active writer.

### 1.5 Concurrency, Locks & Multi-Writer Behavior

#### Locking Mechanism
Codex enforces concurrency safety through advisory file locks in `~/.codex/thread-writer-locks/`:
- `.coordination.lock`: Coordinates global state transitions.
- `<thread_id>.lock`: Dedicated lock file per active thread.
- Codex uses standard BSD/POSIX advisory locking (`flock(fd, LOCK_EX)`).
- Source evidence in native binary: `rollout/src/writer_lock.rs:50`, `writer_lock.rs:176`:
  `"timed out waiting for the thread writer coordination lock; another Codex process may be suspended on this or another host"`.

#### Conflict Behavior
- When two independent processes attempt to write or resume the same thread simultaneously:
  1. Process A acquires `flock` on `<thread_id>.lock`.
  2. Process B attempts non-blocking or timed `flock` acquisition.
  3. If Process A does not release the lock within the timeout window, Process B fails with a timeout exception.
- When using `codex app-server`:
  - `thread/resume` detects if a thread is already running under that app-server instance and **rejoins** it instead of opening a conflicting writer lock.

### 1.7 Active Session Detection

Shardrail can identify whether a session is currently active via three reliable mechanisms:
1. **Advisory Lock Probe (Fastest & Authoritative)**:
   Attempt a non-blocking shared/exclusive lock on `~/.codex/thread-writer-locks/<thread_id>.lock` using `fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB)`.
   - If it raises `BlockingIOError` (EWOULDBLOCK): **Session is actively held by a writer**.
   - If it succeeds: Session is idle (immediately release lock with `LOCK_UN`).
2. **Process Inspection**:
   Run `lsof ~/.codex/thread-writer-locks/<thread_id>.lock` to retrieve the exact PID and process name holding the lock.
3. **App-Server Thread Status**:
   Call `thread/read` or inspect `status` field via `codex app-server`.

### 1.8 Limits, Sizes & Security Boundaries

1. **Encryption at Rest**:
   - `rollout-*.jsonl`, `session_index.jsonl`, `state_5.sqlite`, and `.jsonl.zst` files are **unencrypted plaintext** on disk.
   - Sensitive environment variables, tool outputs, and user prompts are persisted in plaintext.
2. **Chain-of-Thought (Reasoning) Encryption**:
   - In `response_item` of type `reasoning`, raw model reasoning is encrypted by OpenAI's upstream API (`encrypted_content` blob).
   - Only `summary` (if provided) is readable; raw thought tokens cannot be decrypted locally.
3. **File Size & Scalability**:
   - Individual session files range up to 126 MB.
   - Reading files whole into memory will cause OOM or latency spikes. All reading must be streamed or paginated.

### 2.2 Recommended Architecture for Shardrail

#### 1. Reading Strategy (High Performance & Low Overhead)
- **Session List**: Read directly from `~/.codex/state_5.sqlite` (`threads` table) for instantaneous directory queries without spawning external processes.
- **Session History**: Stream lines directly from `~/.codex/sessions/.../rollout-*.jsonl`. For older archived sessions ending in `.zst`, pipe through a streaming Zstandard decompressor.
- **Why**: Avoids daemon spawn latency and token usage; allows reading history even when Codex is offline or unresponsive.

#### 2. Live Sync Strategy
- **Passive Monitoring (Session running in CLI or GUI)**:
  - Tail the active `rollout-*.jsonl` file using byte offsets stored in `thread_history_1.sqlite` projection or filesystem change events (`kqueue` / `inotify`).
  - Active detection via non-blocking `flock` probe on `~/.codex/thread-writer-locks/<thread_id>.lock`.
- **Active Control (Session driven by Shardrail)**:
  - Connect directly to `codex app-server` over `stdio://` or `unix://` and subscribe to `ServerNotification` events (`thread/turn/started`, `thread/item/created`, `turn/progress`).

#### 3. Writing Strategy
- **Exclusive Use of `codex app-server`**:
  - All write operations (sending prompts, resuming sessions, interrupting, approving commands) MUST be executed through `codex app-server`.
  - Direct file editing or SQLite injection must NEVER be attempted for writes.
  - For sessions active in another process, Shardrail must display an "Active in CLI/GUI" warning and require user confirmation to take over or steer.

## 3. Open Risks & Mitigations

1. **Risk: SQLite Projection Schema Drift**:
   - *Detail*: OpenAI may increment `state_5.sqlite` to `state_6.sqlite` in future releases.
   - *Mitigation*: Fall back to reading `~/.codex/session_index.jsonl` and scanning rollout headers if SQLite schema version increments.
2. **Risk: Zstandard Compressed Archives**:
   - *Detail*: 91% of sessions on the test host are compressed with `.zst`.
   - *Mitigation*: Integrate a streaming zstd reader in Rust (`zstd` crate in `Shardrail_Core`) so historical reading transparently decodes `.jsonl.zst`.
3. **Risk: Concurrent Writer Contention**:
   - *Detail*: If a user is typing in `codex resume` or the GUI, starting a turn via Shardrail will fail if the writer lock cannot be acquired.
   - *Mitigation*: Implement the `flock` probe in Shardrail before initiating a write, surfacing a clear lock state indicator to the web UI.
4. **Risk: Plaintext Secret Exposure in Tool Arguments**:
   - *Detail*: API keys and tokens executed via `exec` or tool calls are saved in plaintext JSONL.
   - *Mitigation*: Core daemon must enforce strict redaction before transmitting session turns to relay and web UI.
