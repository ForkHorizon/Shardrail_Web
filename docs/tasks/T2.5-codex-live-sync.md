## 1. Research & Context
- **Official Documentation**: Codex CLI rollout streaming format (`~/.codex/sessions/**/rollout-*.jsonl`), `shardrail_protocol::SessionStreamEvent` specifications, and `T2.1-codex-research.md`.
- **Established Facts**:
  - While Codex CLI or the app runs, new events are appended line-by-line to active JSONL rollout files.
  - Events stream in real time: `turn_context` (declaring turn start), `response_item` (streaming partial or completed outputs), and `task_completed` (marking turn completion).
  - Cursoring: Streaming readers track `byte_offset` and `line_number` to seek and resume without reprocessing historical lines.
  - Deduplication: Codex frequently emits partial response items followed by completed items with the same item ID (`call_id` or `id`). A SHA-256 digest of item contents identifies whether an item is identical (duplicate, suppress) or updated (emit `ItemUpdated`).
  - Resumption & Recovery: If the daemon restarts or the subscriber disconnects, passing the saved cursor seeks directly to `byte_offset`, emitting only newly appended events.

## 2. Design & Acceptance Criteria
- **Scope & Changes**:
  - Implement `CodexLiveSyncEngine` in `crates/session-core/src/codex/live.rs`:
    1. Incremental line-by-line parsing using `BufReader` seeking to `LiveSyncCursor::byte_offset`.
    2. Cursoring tracking `byte_offset`, `line_number`, `last_turn_id`, `turn_ordinal`, and `last_item_id`.
    3. Content-hash deduplication via SHA-256 to drop duplicate items and emit `ItemUpdated` only when item content genuinely changes.
    4. Metrics tracking via `LiveSyncMetrics`: `events_emitted`, `bytes_read`, `lines_processed`, `duplicates_suppressed`, `min_latency_ms`, `max_latency_ms`, `avg_latency_ms`.
    5. Background polling watcher `start_live_watcher` emitting to an async `mpsc::Sender<SessionStreamEvent>`.
  - Wire into `CodexAdapter`:
    - `subscribe(session_id)` and `subscribe_with_cursor(session_id, cursor)`.
    - `get_live_cursor(session_id)` and `get_live_metrics(session_id)`.
- **Acceptance Criteria**:
  - [x] New events from a session that the CLI or the app is writing to appear in Shardrail in real time.
  - [x] Cursors, de-duplication, and recovery after a break.
  - [x] Scenarios tested: write from CLI/app → watch stream; daemon restart in the middle (resumption from cursor); delay/loss of connection (reconnect recovery).
  - [x] Latency and integrity are measured and recorded; no loss, no duplicates.

  - Zero redundant parses: only unread bytes are read from disk during polling.
